# pr-description — design decisions

Maintainer context, not loaded by the skill. Designed 2026-08 against real BI PRs; validated on the Power BI report deployment feature (BI PR branch `nick.wilson/tabular-solutions/pbi-analytic-deployment`). Change the skill with these in view — several read as arbitrary without their reasons.

## The problem it targets

Not "PRs lack descriptions" — the specific failure is that AI-generated diffs no longer evidence intent. A human's 100-file diff implies each line was decided; an agent's doesn't, so review degrades into "does this look reasonable?", which generated code passes easily. The description is therefore a **claim the reviewer can falsify against the diff** — never a summary of it. Every element earns its place by helping a reviewer (human or agent) detect divergence between requirement, claim, and code.

## Decisions and why

- **The anchor (step 1) is a gate, not advice.** Description and code come from the same session, so they share failure modes; the anchor from outside the session breaks the loop. It was originally a warning ("don't invent one") and the first validation run invented one anyway — negations don't hold; gates do. The anchor must also supply a *reason*: a CR that says "add X" gives the what a third time and the why never — that gap goes to the author as a question.
- **Interactive by design.** The agent drafts what the work supports and asks the author for the rest. Only artifact placeholders (screenshots etc.) may survive; missing *text* becomes a question, never a placeholder. This is what keeps the answers honest.
- **Register lives in EXAMPLE.md, not in rules.** Voice guidance loses to demonstrated voice: the first example was written in spec-prose and the skill faithfully reproduced it. To change the output register, rewrite the example. The STE line in step 2 names what the example shows; it can't carry it alone.
- **Budget (2-minute read, 150–300 words)** exists because the first validation run produced 1,100 words of true, well-structured excess. Required-vs-conditional gates *which* elements appear; only the budget bounds *how much* each spends. Large changes earn extra words for the boundary and the risk only.
- **Criteria for success was cut** (2026-08, team feedback): purpose → criteria → argument said the why up to three times — the criteria were the purpose in checkable clothing, and the checks themselves usually sat in the diff. Section 3 now argues change-to-requirement directly ("How does it satisfy the requirement?"), and the concreteness gate carries the checkability the criteria element existed for. *How it was checked* then left interactive mode entirely — tests sit in the diff, and a developer volunteers a hand-run scenario worth telling — and survives in AUTONOMOUS.md, where the run's checks are invisible unless named re-runnably. *Approaches ruled out* was cut in the same pass as too rare to earn a standing element.
- **Where to look hardest** is autonomous-only (2026-08: the interactive version leaned on author self-awareness and was rarely filled well — a developer with a real thin-ice call writes it by hand). In autonomous mode it is *derived from evidence*, never self-assessed: an agent that misread the requirement is confident, not uncertain, about the part it got wrong. Derivation sources: uncovered files, unexercised configurations, out-of-boundary touches.
- **Element labels** (bold, fixed set, lead elements unlabelled) emerged from real drafts, then were formalised: per-element visibility of omissions, and parse anchors for agent reviewers. Labels are descriptive phrases in the reader's tense: the first team review found "The boundary." opaque, and "What must not change" failed on register — the description reports finished work, so a modal label reads as spec, not claim. The label is "What hasn't changed."; these notes keep *boundary* as the internal shorthand. The same rule then retired "The confirmation." — the word presupposes the work was confirmed, when the element's best payload is often that it wasn't. Its label is "How it was checked."; these notes keep *confirmation* as shorthand. Rendering (2026-08): the three section headings are `##` markdown and labels end with a colon, so the two tiers read differently; section 1's heading dropped "(and what isn't)" as unclear.
- **Linear magic words** (2026-08, reviewer feedback on the skill's own PR): a plain reference to a Linear issue automates nothing, so a Linear-tracked anchor is named with a magic word — the same reference then makes GitHub create the link and drive issue state on merge. The word is a claim about the merge — closing words (`Fixes`) assert the merge completes the issue; `Part of` exists for work that doesn't. Magic words register in the PR title, description, and commit messages, never in comments; a markdown-linked ID counts.
- **The boundary claims reach, not file lists** (2026-08, first live use): the skill's own PR filled the element with "the three existing skills do not change" — provable from the diff's file list in a glance, and useless. The element's test is *could the changed code plausibly reach it?* — a claim earns its sentence only when the file list can't prove it. The same test then demoted the element from required to conditional: a purely additive PR has nothing in reach, and requiring the element there forces inventory or stretch. The demotion is safe because the trigger is diff-checkable — a reviewer can see whether existing code is modified, so a missing element stays challengeable, which was the reason it was required.
- **Concreteness, not length, gates verbosity** (2026-08, reviewer feedback on the skill's own PR): the first team-reviewed description sat inside the word budget and still read as verbose — the excess was abstraction, sentences about the description's own elements rather than the work. The budget bounds length only, so step 4 gained a checkable gate: every sentence names something the reviewer can open. The register stays demonstrated in EXAMPLE.md, which now names the property. Watch docs-shaped PRs: a diff with no runtime behaviour starves the argument element and abstraction fills the gap — if the gate doesn't hold there, they join the parked variants.

## Deliberately excluded

- **Refactors with no intended behaviour change** — the three sections collapse into "nothing changes" three times. Parked until the skill has been used enough to design the variant. The real review question there is "is it actually behaviour-preserving?", which wants a different section 3.
- **PR titles** — parked; revisit if they prove a problem. Note GitHub (as configured for BI) puts only the title in the merge commit, so titles are the entire `git log` record.
- **AI-provenance disclosure** ("which parts were generated") — declined, not parked: it degrades to noise once everything is partly generated, and *where to look hardest* asks the useful question directly.
